# E-paper H_WALL_BRICKS — Raspberry Pi Zero 2 W 版

六角形カラー電子ペーパーパネル(H_WALL_BRICKS / MCB03、DeviceType `0x01`)を
**Raspberry Pi Zero 2 W からスタンドアロン制御**するためのリポジトリ。

PC版リポジトリ([E-paper_H_WALL_BRICKS](https://github.com/Yoshi-Hirata/E-paper_H_WALL_BRICKS))
で実証済みの Python ホストツール群を移植し、Pi 上での常時運転
(電源投入で自動開始)に対応させる。

## なぜ Raspberry Pi か

M5StickS3 + RS485/TTL でのスタンドアロン化を試みたが、基板間リンクは
未文書化の独自プロトコル(3.3V TTL UART 9600bps + 未知の実行トリガ 0x1E +
不明な受理条件)であり、外部マイコンからの直接制御は現時点で不可能と判明
(詳細は PC 版リポジトリの docs/DEVELOPMENT.md 8章)。

一方、**USB CDC 経由(→基板 0x01 →中継→基板 0x02)の制御は完全に動作実績が
ある**ため、PC を Raspberry Pi に置き換えるのが最短・最確実の構成。
両パネルとも制御できる。

## ハードウェア構成

```
Pi Zero 2 W ──USB OTG(micro-B "USB"ポート)── 基板 ID:1 ──4芯ケーブル── 基板 ID:2 … ID:20
```

1 着の衣装は基板最大 60 枚(DIP スイッチで ID 1〜n、番号は連番)。機体のソフトは
`--boards` を与えなければ **ID 1 から上へ探索**し、最後に応答した基板の先 6 個が続けて
無応答なら打ち切る(21 枚なら 27 回の探索)。**応答しない基板はスキップして残りだけで
動く**。ショー PC から基板一覧が来たら、それに従う。欠けている基板は 60 秒ごとに軽い再プローブで
探し続け、後から電源が入れば自動的に演出へ参加する(待機中なら白を描き直す)。
対象を絞りたいときは `--boards 1 20` のように指定する。

- Pi の給電は "PWR" と刻印された micro-USB に 5V/2.5A 以上の AC アダプタ
- 基板との接続は **"USB" と刻印された micro-USB(OTG)** に、
  OTG アダプタ + USB-C ケーブルで基板 ID:1 へ
- パネル制御基板の電源は従来どおり専用電源から供給(USB は通信のみ)
- 基板 ID:1 は DIP スイッチ = 1(バスマスタ)であること

## セットアップ

**Radxa Cubie A7Z を使う場合は [radxa/README.md](radxa/README.md) の
「セットアップ手順」を参照**(SPI オーバーレイ・GPIO の叩き方・Wi-Fi の
扱いが Pi と異なる)。以下は Raspberry Pi 向け。


1. Raspberry Pi OS Lite (64-bit) を microSD に書き込み
   (Raspberry Pi Imager で Wi-Fi / SSH / ホスト名を事前設定しておくと楽)
2. SSH でログインし、本リポジトリを取得:

   ```bash
   sudo apt update && sudo apt install -y git
   git clone https://github.com/Yoshi-Hirata/E-paper_H_WALL_BRICKS_Raspi.git
   cd E-paper_H_WALL_BRICKS_Raspi
   ```

3. セットアップスクリプトを実行(venv 作成、依存導入、シリアル権限、
   systemd サービス登録まで一括):

   ```bash
   ./raspi/setup.sh
   ```

4. 動作確認(基板を USB 接続した状態で):

   ```bash
   .venv/bin/python host/stop.py --addr 1     # ACK_SUCCESS が返ればOK
   .venv/bin/python host/wave_demo.py --cycles 3
   ```

## LCD HAT の UI(Waveshare 1.3inch LCD HAT)

240x240 の IPS LCD + ジョイスティック + KEY1〜3 でデモを操作する。

### 待機状態(全面白)

パネル基板は電源投入だけでメーカーのデモを自動再生し始めるため、
放っておくと「待機中」がショーの背景として使えない映像になる。
そこで **Pi / Radxa が基板との接続を確立した時点で自動的に**
再生を止め、両面の全セクターを白にして停止させる。これを待機状態とする。

- `python -m ui.main` 起動時、`--pattern` が指定されていなければ実行される
- メニュー画面の下段に `standby: blanking + check 0/20...` →
  `standby: white, boards 2/20 OK` と表示(数字は 応答基板数/設定基板数。
  通信エラーがあれば `ERROR ...` が赤で出る)
- **メニュー最上段の `STANDBY` を選んで KEY1** でいつでも再実行できる
  (全セクター白 + 全基板の通信チェック)。デモと違い画面はメニューに
  留まり、結果が上記のステータス行に出る
- 白の描画は 1 回だけ。書き込み後にガード時間(既定 12 秒)を置いて再度
  停止指令を送り、リフレッシュ完了後にメーカーデモへ戻るのを防ぐ
- 基板がリフレッシュ中(9.8 秒間は無応答)でもリトライして必ず白にする
- 応答しない基板はスキップし、居る基板だけを白にする。以後 60 秒ごとに
  再プローブし、後から現れた基板は白を描き直して待機に取り込む
- **USB を抜き差ししても白に戻る**。基板は電源が切れるとメーカーデモを
  再生しながら復帰するので、待機中はデバイスノード
  (`/dev/ttyACM*`)を 2 秒ごとに監視し、消失または再列挙を検知したら
  白を描き直す。検知漏れの保険として 60 秒ごとに停止指令も送る
- 白にしたくない場合は `--no-standby`

> 監視は待機中のみ。デモ実行中に抜き差しした場合はバスを開き直して
> **次のサイクルで描き直される**。デモの**一時停止中**は次のサイクルが
> 来ないため、KEY1 で再開するまでメーカーデモが流れたままになる。

| 操作 | 動作 |
|---|---|
| ジョイスティック 上下左右 | デモパターンの選択(ラップする) |
| **KEY1** | 開始 → 一時停止 → 再開(サイクル数とタイマーを保持) |
| **KEY1 を 1 秒長押し** | リセット(ゼロから開始) |
| KEY2 | メニューに戻る(実行中のデモは停止) |
| KEY3 | バックライト消灯(どのボタンでも復帰) |

メニュー末尾の行は、デモではなく**機体そのものの操作**:

| 行 | 動作 |
|---|---|
| `UPDATE FW` | 基板の FW を OTA で書き込む(485 を抜いて 1 枚ずつ)。確認画面で **LEFT / RIGHT** が書き込む版(`FW/FW_*` にある全部、既定は最新)、UP / DOWN が基板 |
| `FW VERSION` | 応答した基板の FW を一覧。V1.4(FW_260923 以降)は `V1.4 16-color`、それ以前は `V1.1` と出る(USB 直結の 1 枚に 0x25 で判別) |
| `GIT PULL` | `git pull --ff-only`。更新があれば KEY1 で UI を再起動 |
| **`REBOOT`** | **機体(OS)を再起動**。確認画面で **KEY1 を 1 秒長押し**したときだけ実行(短押しでは何も起きない)。KEY2 で中止 |

`REBOOT` は `sudo -n systemctl reboot` を呼ぶので、パスワード不要の sudo が
前提(Radxa は `radxa/README.md` のセットアップ手順 3、Pi OS は既定で可)。
拒否された場合は画面に `FAILED` と理由が出て、長押しで再試行できる。
再起動後は通常起動と同じく**待機(全面白)**に入る(`--pattern` /
`--no-standby` 運用の機体はそれぞれの挙動)。約 1 分で UI が戻る。

実行画面には**経過タイマー(時:分:秒)**、サイクル数、直近のログが表示され、
通信エラーは赤で強調される。一時停止中は `PAUSED` と表示され、
**停止していた時間は経過時間に加算されない**。

消灯からの復帰に使った押下は**消費される**ので、暗い場所で手探りしても
デモの状態は変わらない。

### ショー運用・バッテリー運用のオプション

`/etc/default/epaper-ui` の `UI_ARGS` に追加する:

| オプション | 用途 |
|---|---|
| `--locked` | ボタンを無効化(接触事故でデモが止まるのを防ぐ)。解除は KEY2→KEY3→KEY2、1 分の無操作で自動再ロック |
| `--blank-after 10` | 10 秒無操作でバックライト消灯。**既定はオフ**。バッテリー運用で 20〜40mA の節約 |
| `--no-standby` | 起動時に全面白へ落とさず、パネルの表示をそのままにする(メーカーデモが流れ続ける) |

追加後は `sudo systemctl restart epaper-ui`。

選択できるパターン:

| パターン | 内容 | 切替間隔 |
|---|---|---|
| `SOLID+RANDOM` | **単色6色 → ランダム6回 を無限ループ**(常時デモの既定) | 各ステップ準拠 |
| `WAVE` | ID:1 グラデーション + ID:2 スパイラル | 既定値 |
| `GRADIENT` | 両面とも中心から広がる同心円 | 既定値 |
| `SPIRAL` | 両面とも外周から中心へ時計回り | 既定値 |
| `MIRROR` | 位相をずらしたグラデーションが追いかける | 既定値 |
| `RANDOM` | 各三角形をランダムな色に | 20 秒 |
| `SOLID` | 2枚とも全面単色を 白→黄→青→赤→黒→緑 の順に巡回 | 15 秒 |

既定値は `--interval`(既定 60 秒)。`SOLID`/`RANDOM` はパターン側で
間隔を指定している(`ui/patterns.py` の `Pattern.interval`)。
`SOLID+RANDOM` は `Playlist` で、各ステップが自分の間隔を保ったまま
順番に流れる(1周 = 単色90秒 + ランダム120秒 = 約3分30秒)。

ループの構成を変えるには `ui/patterns.py` の
`Playlist("loop", ..., steps=((_SOLID, 6), (_RANDOM, 6)))` を編集する
(タプルは「パターン, そのパターンを何サイクル続けるか」)。

**リフレッシュ所要時間の実測値**: 全面書き換えは色によらず、
初代基板 **9.8 秒**(2026-08-04)、本番基板 **約 16 秒**(2026-08-14)、
**最新 FW では約 7 秒**(2026-09-21 報告)。
64 バイト配列の保存が約 0.2 秒。本番基板では 1 サイクルの物理的下限は
約 17 秒で、15 秒間隔の SOLID は実質リフレッシュ律速になる。

**リフレッシュ中のコマンドは破棄されず、受信バッファに溜まって完了後に
実行される**(2026-08-14 実測)。show ブロードキャストを保険で複数回
送ると、その回数だけ全面再描画が繰り返され、基板間で描画回数がずれて
「基板間ラグ」に見える。show は 1 サイクル 1 回だけ送ること。

なお毎サイクル 2 枚分のフラッシュ書き込みが発生するため、常時運転する
場合は間隔を長めにすること。

### 起動

```bash
.venv/bin/python -m ui.main --check         # パネル/SPI/GPIO/LCD の準備状況を診断
.venv/bin/python -m ui.main                 # HAT があれば LCD、無ければ PNG+キーボード
.venv/bin/python -m ui.main --display png --frames /tmp/ui   # HAT 無しで動作確認
.venv/bin/python -m ui.main --preview /tmp/ui                # 画面サンプルを書き出して終了
```

**HAT を挿したら、まず `--check` を実行すること。** 全項目が `ready` なら
そのまま `python -m ui.main` で動く。`gpio pins: BUSY` と出た場合は他の
プロセスがピンを掴んでいる(下記の HAT 競合を参照)。

### ⚠️ 他の Waveshare HAT との競合

このリポジトリの Pi には元々 **Waveshare 7.5inch e-Paper HAT**(気象
ダッシュボード)が載っており、1.3inch LCD HAT と**物理的に競合する**:

| 信号 | 7.5inch e-Paper HAT | 1.3inch LCD HAT |
|---|---|---|
| GPIO25 | DC | DC |
| GPIO24 | BUSY | BL(バックライト) |
| GPIO8 | CS (SPI0 CE0) | CS (SPI0 CE0) |

40 ピンヘッダも 1 枚しか挿せないため**共存は不可**。本プロジェクトを
優先する方針とし、2026-08-04 に気象ダッシュボードの cron を無効化した
(削除ではなくコメントアウト。root の crontab を
`/home/r2/dashboard/crontab-root.backup-*` にバックアップ済み。
アプリ本体は `~/dashboard` に残置、git から復元も可能)。

戻す場合は `sudo crontab -e` でコメントを外す。

**HAT が届く前でも開発・確認できる**: `--display png` は毎フレームを
`/tmp/ui/latest.png` に書き出し、`--input keyboard` は標準入力で操作できる
(`w`/`s` 選択、`1`/`2`/`3` = KEY1〜3、いずれも Enter で確定)。

### ピン配置(Waveshare 1.3inch LCD HAT / BCM)

| 信号 | ピン | 信号 | ピン |
|---|---|---|---|
| LCD SPI | SPI0 (CE0) | KEY1 | GPIO21 |
| LCD DC | GPIO25 | KEY2 | GPIO20 |
| LCD RST | GPIO27 | KEY3 | GPIO16 |
| LCD BL | GPIO24 | 上/下 | GPIO6 / GPIO19 |
| | | 左/右 | GPIO5 / GPIO26 |
| | | 中央押し | GPIO13 |

SPI の有効化(`dtparam=spi=on`)は `raspi/setup.sh` が行う(要再起動)。
画面の向きが合わない場合は `ui/display.py` の `ST7789Display(madctl=...)`
を変更する(既定 `0x70`)。

**gpiozero には `lgpio` が必須**(requirements に含む)。無いと gpiozero が
実験的な native factory にフォールバックし、ボタンの `Button()` が
すべて `EINVAL` で失敗する(症状: ボタンが一切効かない)。

### HAT 未着時点での検証状況(2026-08-04)

LCD 本体は未接続だが、以下は実機で確認済み:

- ST7789 ドライバは実 SPI/GPIO 上で init → フレーム転送 → クローズまで
  例外なく完走(init 538ms、1 フレーム約 150ms)
- 8 個の入力ピン + DC/RST/BL の計 11 ピンすべて確保・解放できる
- UI からデモを起動し、**実際の電子ペーパーパネル 2 枚が 3 サイクル更新**
  (ジョイスティック選択 → KEY1 開始 → KEY3 終了までスクリプト入力で再現)
- `epaper-ui.service` が起動し PNG フレームを出力(HAT 無し時の自動退避)

残るのは LCD の表示そのもの(向き・色・視認性)の確認のみ。

## ルック(衣装)の CSV 取り込み — `conductor/`

ショーでは 1 ルック = Radxa 1 台(基板 最大 60 枚 × 鱗 60 枚)。デザイナーから
届く 2 種類の CSV を、基板ごとの 64 バイト配列に変換する(PC 側で実行)。

| ファイル | 内容 |
|---|---|
| `LookNN_map.csv` | `side,row,col,board_no,socket,label[,shift]` — 鱗 1 枚 = 1 行。衣装上の位置と、どの基板のどのソケットか。7 列目 `shift`(0 / 0.5)は制作サイトの行ごとの半マスずらし(中央マスのある行 0、ない行 0.5)。無い map は奇数行 0.5 の既定で描く。配線ビューとデザイン前のサムネイルはこの値、デザイン表示はデザイン CSV 自身の shift を使う |
| `LookNN_color_NAME_grid.csv` | `side,row,shift,1,2,3,…` — 衣装の 1 段 = 1 行。セルは色コード `0x00`〜`0x0F`、**穴の無いマスは `0`、色未指定は `-`**(先方 README の定義)。キューごとに 1 ファイル |

ファイル名の `_map` / `_color_` より前がアイテム名(`Look22`、
(制作サイトの書き出しに合わせて **型番**を使う: `AZ271SD1305_map.csv`、`AZ271SD1305_B_color_…_grid.csv`)
デザインの `_color_` と `_grid` の間が、そのデザインの名前(`pattern01` なら `P01`、
`ref_multicolor_redorange_s22` ならそのまま)。配線ナビの書き出し名がそのまま使える
(`AZ271SD1305_color_ref_multicolor_redorange_s22_grid_A-1.csv` など。先頭が型番の
ファイルは「Add CSV to this item」でアイテムに入れる)。
`Look20-Skirt`、バッグの名前など)で、map と grid はこの名前で対応付ける。

- 2 つは `(side, row, col)` で結合する。row 0 が裾、最大の row が首側
- **CSV は内側(体側)から見た向き**。客席から見ると左右が逆なので、
  プレビューは既定で反転して「外側(客席から)」を描く
- **1 機体に複数アイテム**(Look20 = トップス + スカート)を載せる場合、
  DIP の ID は**機体のバス全体で通し番号**(スカート 001〜016 → ID 1〜16、
  トップス 076〜091 → ID 17〜32)。アイテムごとに 1 から振ると衝突する
- `board_no` は基板の固有番号。**ルック内で昇順に並べた順位が DIP の ID**
  (017→1、018→2 …。飛び番があっても ID は詰める)
- `socket` N = 配列インデックス N(P1〜P60、DeviceType 0x03)。鱗の無い
  ソケットは `0xFF`(非更新)
- 色は `FW/FW_260917/260917_16_Color_Chart_ changed.xlsx` の表
  (**0x05 = 緑、0x06 = ターコイズ**)
- **`0` は「穴なし」、白は `0x00`**。取り違えを防ぐため、map に鱗があるのに
  grid に色が無い(`0` や `-`)/grid に穴があるのに map に鱗が無い、は
  どちらもエラー。一部の鱗だけ変えるキューは `--partial`(色の無い鱗は現状維持)

**Web UI(PC 上、localhost のみ)**: CSV をドロップして取り込み、検証結果・
仕上がり/配線プレビュー・DIP 設定表を確認し、アイテムを機体
(`radxa-01`〜`10`)に割り当てる。データは `./showdata`(git 管理外)に置く。

```bash
python -m conductor serve        # http://127.0.0.1:8765
```

**起動はリポジトリ直下の `Start Conductor.bat` をダブルクリック**(中身は
`python -m conductor serve --open`)。サーバを起動して既定のブラウザでページを開く。
既に起動中なら新しいサーバは立てず、ページを開くだけ。黒いウィンドウを閉じると UI が
止まる(開始済みのショーは各機体が自走するので止まらない)。

起動・停止・開けないときの対処は **docs/CONDUCTOR_START.md**。

UI の表記はすべて英語。タブは **Designs**(デザイン確認)/ **Timeline** / **Units**(機体)。

**Designs** タブの左の一覧は、機体 radxa-01 → 10 の順に並んだアイテムのカード
(どの機体かはカードのプルダウンに出る。何も着ていない機体は細い点線の枠)。アイテムには **LOOK 番号**と**型番**
(`AZ271SD1301` など)を併記し、どちらもその場でクリックして書き換えられる
(`showdata/show.json` の `labels` に保存。Undo / Redo の対象)。これは表示名で、
map とデザインを結び付けるのは従来どおり CSV のファイル名の先頭(`Look19`)。
ラベルを付けるまでは、ファイル名の `LookNN` の数字が LOOK 番号として出る。

並び替えはドラッグ&ドロップ: カード右上の `⠿` をつかんで別の機体の枠へ落とすと、
その機体が着ているもの全部(トップスとスカートは 2 点一緒)がそこへ移り、間にある
ものは 1 つずつずれる(10 枠のリストの並べ替え)。Unassigned のアイテムは、落とした
機体に加わる。どちらも Undo 1 手(`POST /api/arrange`)。1 点だけを別の機体へ移す・
2 点を 1 台にまとめるのは、カードのプルダウンでもできる。

同じ型の衣装が 2 着あるとき(同じ型番を 2 人が着る)は、カードの **Duplicate**。map CSV を
別名でコピーして(`Look22_map.csv` → `Look22-2_map.csv`)、**独立したアイテム**を作る。
以後は何も共有しない: デザイン CSV・キュー・機体・LOOK 番号・基板番号はそれぞれのもの。

- デザイナーから届く CSV は 2 着とも同じ名前(`Look22_color_pattern01_grid.csv`)になりうるので、
  アイテムを選んで **Add CSV to this item** から入れる。ファイル名の先頭がそのアイテムの名前に
  付け替えられて保存される(`Look22-2_color_pattern01_grid.csv`)。右上の `Add CSV` と
  ページへのドロップは、従来どおりファイル名どおりのアイテムに入る
- 実際に縫い付けた基板が map CSV と違うとき(同じ map から作った 2 着目、予備基板への交換)は、
  基板表(BOARDS AND DIP SWITCHES)の BOARD NO. をその場で書き換える。CSV は書き換えず
  `show.json` の `boards` に保存(Undo 対象)。DIP ID は書き換えた番号の小さい順に振り直される
- **デザイン一覧は 1 デザイン = 2 行の帯**(表と 2 列グリッドはやめた): 1 行目に
  ラベル・状態・タイムライン使用状況、2 行目にファイル名(省略記号つき 1 行)、右に
  Transition(Sequence・Span)と削除。1366 px 幅でも横スクロールなしで全部届く。
  同じ Transition の操作は、ガーメント上のツールバー(選択中のデザインのみ)からも
  1 か所に集約

**Timeline** タブ: アイテムごとに 1 本のトラックがあり、1 アイテムに
何枚でも取り込めるデザイン(`*_color_NAME_grid.csv`)を、ショー開始からの
経過時刻に割り当てる(`showdata/show.json` に保存)。

- キューは「Start → 書き換え(+ 遷移)→ Complete → 表示を保持 → End」の 1 区間。
  **Start** = 指令を送る瞬間(E ペーパーが書き換えを始める)。**Refresh** = このキューの
  書き換え時間(既定はショーの「Default refresh time」、FW や設定で差が出るのでキューごとに
  手入力で上書きできる)。**Complete** = Start + Refresh + Span(表示のみ)。**End** = この
  デザインの終わり = 同じアイテムの次のキューの Start(最後のキューはショーの終わりまで)。
  End を書き換えると次のキューの Start が動く(Complete より前には置けない)。トラックの帯は
  Start→Complete を斜線(書き換え中)、Complete→End をベタで描く。0:00 のキューはプリセット
  (START の前に表示)。トラックをクリックでキュー追加、ドラッグで Start を移動(5 秒刻み)
- **遷移は CSV(デザイン)ごとの設定**: Designs タブのデザイン一覧の Transition 列で、
  **Sequence**(順序 6 種: ソケット順 = 現状の P01→P60 / 図心から放射状 / 上→下 / 下→上 /
  左→右 / 右→左。左右は客席から見た向きで面ごと、図心は前面のもの)と **Span**(秒 = 最初の行・
  列・リングへの指令から最後への指令までのギャップ)を決める。キューは参照するデザインの設定を
  **Transition: design default** で継承し、**custom** で上書きできる(両方の値は保持される)。
  遷移つきのキューは「書き換え 7 秒 + Span」だけ長くかかり、帯もその分伸びる。Span は FW の
  制約で **最大 30 秒**(超えるとキューの問題として表示)。基板へは 10 ms 刻み(uint16)の遅延表を
  V1.4 の 0x1F で送る。実機で動かすには基板 FW **FW_260923(V1.4)以降**が要り、古い FW では
  遷移は無視されて P01→P60 で変わる(機体の `/status` の `no_sweep` にその基板が出る)
  Designs タブの **Prepare**(手動発火)でも同じ遷移で変わる。基板が遅延表を受け取ると機体の
  ログに「board N: sweep table saved, 60 sockets, last starts +3.00 s」のように出る
- **色味は実機見本色**: 画面の 16 色は制作サイトの色表 260921(実機を肉眼で見た色)に合わせてある。
  白も紙の上では薄い鋼青に見えるので、その色で描く。基板に送るのは色コードで、見た目の RGB は
  画面と PNG プレビューだけの話
- **再生位置はトラック上の赤いバー**: 目盛り行にある赤い三角のつまみをドラッグ(または目盛りを押したまま
  左右へ)で任意の時刻へ。ルック・時刻・音楽が追従し、再生中なら離した位置から続く。← / → で 1 秒、
  Shift 併用で 5 秒、Home で 0:00。下部ドックのスライダーはトラックが隠れる Simulator view のときだけ
- **画面の組み立て**: 「THE LOOKS AT」(ルック 6 枠と再生操作)は画面下部の**ドック**として常に見える。
  ▾ Collapse で操作バーだけ(36 px 程度)に畳め、Simulator view で全画面。EDIT CUE は幅 1400 px 以上
  ではトラックの右横に固定表示(スクロールしても追従)、それより狭い画面ではトラックの下。EDIT CUE の
  見出しをクリックすると折りたたみ、キューをクリックすれば開く。Esc で選択解除
- **EDIT CUE の Transition**: 「this design(このデザインを使う全キュー)」を選ぶと、ここで変えた順序と
  秒数がデザインの設定として保存され、Designs タブの一覧・ツールバー・同じデザインの他のキューに
  同時に反映される(逆も同じ。Undo 可)。「this cue only」はこのキューだけの上書き
- **再生シミュレーター**: 「THE LOOKS AT」の **Play / Pause / Stop**(Space でも可)で再生位置が
  実時間で進み、下段の各ルックが実際と同じタイミングで変わる(遷移の途中経過、一部更新の
  重ね合わせ込み)。再生中でもキューの追加・移動はできる。スライダーで任意の時刻へ
  - **書き換え中の見え方も再現**: 実物の動画(AZ271SD1307)から起こしたモデルで、各鱗が
    濃紺 → まだらのチカチカ → 黄・茶寄り → 目標色が黄緑がかって浮かぶ → 最終色、と
    リフレッシュ時間いっぱいかけて変わる。開始時刻は鱗ごとに遷移の遅延(上→下、客席右→左、
    図心から放射状 …)+わずかなばらつきに従うので、設定した方向の波として見える。
    一部更新のキューでは色を持つ鱗だけが書き換わる。Units タブの LOOK 行も同じ
- **ショーの音楽**: 同じ場所の **Load music** で音声ファイル(MP3 など、64 MB まで)を
  アップロードすると(`showdata/music/` に保存)、再生が音楽と同期する(再生位置は音声の時刻に
  従い、スライダーで音楽ごとシークできる)。Replace / Remove で差し替え・解除
- **演出の保存と復元**: **Save show…** でタイムライン・遷移・LOOK 番号と型番・機体の割り当て・
  基板番号・ショーの長さ・書き換え時間を 1 つの JSON(`showdata-show-YYYYMMDD-HHMM.json`)に
  ダウンロード。**Load show…** で読み戻す(確認のあと 1 手で置き換え、Undo で戻せる。音楽
  ファイル自体は含まないので別途アップロード)。ワークスペースにない CSV を参照するキューは
  警告つきで取り込まれ、Timeline に問題として出る
- **書き換え時間**(送信から絵の完成まで)はショーの設定値で、既定 **7 秒**
  (最新 FW)。FW で変わってきた値なので(9.8 → 16 → 7 秒)、タイムライン画面の
  「書き換え時間」欄で変更できる。旧 FW の基板が混ざるなら長い方に合わせる
- **色データは Upload の時点で基板に書き込み済み**(2026-09-24、依頼者の方針:
  「毎回リアルタイムに書き込みを行うのはショーにおいてリスクが高い」。
  Meris 回答 2026-09-24: 20 スロットは全て同一で書き込み時期を問わず安全)。
  ① Upload を押すと、各機体のタイムラインの 1 キュー = 1 枚として、キュー順に
  スロット **1〜18** へ焼き込む(スロット 0 は白のスタンバイ専用、19 は
  Designs タブの Prepare・スタンドアロンデモの単発表示専用)。ショー実行中の
  送信はスロット番号だけを持つトリガ 1 発になり、そこでは何も書き込まない。
  ショーが動いている間の Upload は「stop the show first」で拒否される
  (① Upload ボタンは run 中 disabled)。挿入で途中のキューの slot 番号が
  ずれると全体を焼き直す(1 機体あたり約 3 分)ため、末尾への追加やその場の
  編集の方が速い。Units タブの各機体タイルに **Pictures** 行(writing n / N・
  written・FAILED)が出て、「THE SHOW」カードにも「pictures written on
  n / m units」が出る(burn を報告している機体のみを分母にする)。START は
  書き込み中の機体・失敗した基板がある機体・オフラインの機体・このショーを
  まだ受け取っていない機体があれば機体名つきで拒否される(書き込み中は
  `force` でも越えられない。基板の書き込み失敗だけは、ページで確認したうえで
  `force` により「start anyway」できる)
- 検証(`conductor/timeline.py`): 書き込みはもう実行中に起きないので、同じ機体の
  送信間隔は基板数によらず「書き換え時間 + ディレクターの余裕 1 秒」だけで済む
  (7 秒 refresh なら常に 8 秒。プリセット直後の最初のキューも同じで、以前あった
  「本体の合流待ち」ぶんの上乗せはなくなった)。同時刻に複数アイテムが送る場合
  (Look20 の上下など)は、その瞬間の全キューのうち一番遅い refresh・一番長い
  スイープで次までの間隔が決まる。一方で基板が持てる絵は 18 枚
  (スロット 1〜18。0 は白、19 は手動専用)までなので、1 機体のタイムラインが
  19 枚目の絵を要求すると問題として出る(プリセットも 1 枚に数え、同時刻の
  複数アイテムは 1 枚として数える)。ほかに、
  未取り込みのデザイン、色未指定(`-`)の残るデザインを通常キューで使う、同じ
  アイテムの次のキューが前の絵の完成より前に始まる、キューごとの書き換え時間が
  1〜60 s の外、ショー終了後の時刻、0:00 プリセットなし(警告)を検出する
- **元に戻す / やり直す**(ヘッダのボタン、Ctrl+Z / Ctrl+Y / Ctrl+Shift+Z):
  タイムライン・ショーの長さ・機体の割り当てが対象。履歴は
  `showdata/history.json` に最大 200 手、ページの再読み込みやサーバの再起動を
  またいで残る。CSV の追加・削除は対象外(削除は確認ダイアログあり)
- `-` の残るデザインは「一部更新用」として扱い、キューにすると自動で
  一部更新になる(色の無い鱗は直前の表示のまま)

**Units** タブ(P1b): 10 台のエージェントを 2 秒ごとに問い合わせ、オンライン状態・
応答している基板数・コミット・**時計のずれの測定精度**を表示する。手動の一斉表示は
2 段階: **Prepare**(アイテムごとに選んだデザインを各機体の基板へ保存。表示は
変わらない)→ **GO**(N 秒後の同じ瞬間に全機体が表示命令を 1 回だけ送る)。
ほかに「Cancel the fire」「All units STANDBY (white)」「Release all units to their own menu」。
機体の宛先は既定で `radxa-NN` = `192.168.51.(100+NN):8787`、変える場合は
`showdata/fleet.json`(`{"units": {"radxa-01": "host:port"}, "token": "..."}`)。

**ショーの進行**(Units タブの上段「THE SHOW」、P2): タイムラインを機体ごとの
**ショーファイル**にまとめて配り、あとは各機体が自分の時計で実行する。
本番中に PC や Wi-Fi が落ちてもショーは最後まで進む。

| 操作 | 動作 |
|---|---|
| ① Upload | タイムラインに問題が無ければ、機体ごとのショーファイル(全キューの配列 + 各キュー後の全体像)を送る。機体はディスク(`~/.epaper/`)に保存 |
| ② Show preset | 0:00 の姿を先に出しておく(START で書き換えが起きない) |
| ③ START | N 秒後を T0(ショーの 0 秒)として全機体へ渡す。以後、各機体が「キューの送信時刻の少し前に基板へ保存 → 時刻ちょうどに表示命令」を自律実行 |
| HOLD / RESUME | 進行を保留 / 保留した時間だけ全体を後ろへずらして再開 |
| NEXT ▶ | いちばん近い次のキューを N 秒後に繰り上げる(全機体の T0 を同じだけ早める) |
| STOP | 進行を止める。パネルの表示はそのまま。「全機体 STANDBY(白)」は停止してから白にする |
| SEEK(Manual control) | チェックを入れて解禁するバーで再生位置を手で動かす(`POST /api/fleet/seek`)。実行中は全機体の T0 を動かして送り直し、HOLD 中は保留した位置だけ動かして何も送らず、未実行なら次の START が始まる位置を覚えるだけ。バーはドラッグ中はプレビューのみ、離した瞬間にコマンドが 1 回だけ飛ぶ |

- HOLD / RESUME / NEXT / SEEK はどれも「T0 を動かす」だけ。機体側の規則は 1 つ:
  時計を見て「いま出ているべきキュー」と「次のキュー」を求め、足りないことをする
- SEEK で位置を決めてから START すると、その位置から始まる(③ の表示が
  「START FROM 3:00」に変わって知らせる)。START・STOP のどちらもその位置を忘れる
  (次の START は 0:00 から)。0:00 以外から始めるのも Manual control が要る
- **復帰**: 機体が途中で再起動しても、ディスクのショーファイルと T0(実時刻で保存)から
  自分で合流し、出ているべき**全体像**を 1 回の書き換えで出す。再起動直後の T0 は
  粗いので数秒待ち、その間に PC が正確な T0 を送り直す
- **自動修復**: PC は 2 秒ごとの問い合わせで各機体の T0 とショーの版を見ており、
  ずれ(50 ms 超)・未開始・旧版・未配布を見つけたら頼まれなくても直す
  (画面に「Corrected automatically: …」と出る)。PC のアプリを再起動しても、実行中の T0 を機体から復元する
- 一部更新のキューでも機体の**全基板**に書く(変えない基板には「何も更新しない」
  配列)。表示命令がブロードキャストなので、古い配列が残った基板が再描画するのを防ぐ
- ショーの実行中は「MANUAL CUE」(Prepare / GO)は拒否される(先に STOP)
- 「THE SHOW」カードに **LOOK ごとの小さいサムネイル行**(高さ固定 120 px)を表示。
  Timeline タブの再生シミュレーターと同じ位置で色が変わり、いま何を着ているかが
  一目でわかる。機体オフライン・書き換え中はセルに状態表示が乗る

**スタンドアローンデモ**(Units タブ、THE SHOW の下の「STANDALONE DEMO」カード):
いまのタイムラインを機体ごとのショーファイルとして各機体自身のメニューに書き込む。
以後はその機体単体で(この PC なしに)自分の分だけ再生できる。名前は書き込み時に
決める(**A〜Z・0〜9・記号、最大 14 文字** — 機体の LCD フォントは日本語を描けないため、
日本語や 15 文字以上は拒否される)。「Write demo to units」はタイムラインに問題が
残っている間(① Upload と同じ判定)、名前が空の間、**ショーが進行中の間**は押せない
(まず STOP)。「Loop」を付けると終了 5 秒後に自動で最初から再生し直す。書き込み結果は
機体ごとに 1 行(OK / FAILED)。下の「Demos on the units」表は各機体の `GET
/demo/list` を集めたもので、名前・キュー数・長さ・ループ・保持している機体・
削除ボタンを 1 デモ 1 行で示す(Refresh で再取得。書き込み・削除のあとは自動で更新。
キュー数・長さ・ループは機体ごとに数字が違うことがあるので機体の並び順のまま
`16 · 16 · 27` のように出す)。**Timeline** 列は、そのデモが書き込まれた時点の
タイムラインといまのタイムラインが一致するか(`current` / `older`)を機体ごとの版で
照合したもの(この PC が直前にアップロードした版があればそれと比較、無ければその場で
タイムラインをコンパイルして比較 — 比較材料が無い、またはタイムラインに問題が
残っている間は `older` ではなく「—」)。機体のタイルにも「Demos」行(保持している
デモの数。旧いエージェントは値を返さないので「—」)。表の取得に失敗した機体は
「Offline」(応答なし)と「Not checked」(応答はあったが失敗、旧いエージェントの
404 など)を分けて出す。

- 機体側の再生: LCD メニューの STANDBY のすぐ下にデモの行が並ぶ(`ui/demos.py` ・
  `ui/agent.py` 側の実装)。**KEY1** で 0:00 から再生開始、**KEY2** で停止しメニューへ、
  **KEY1 長押し**で最初からやり直し。Loop 付きのデモは終了 5 秒後に自動で再開する
- **デモ再生中の機体には PC の進行が割り込まない**: ある機体がデモを再生中
  (LCD の状態が running/holding)は、その機体だけ Upload・START・SEEK・
  RESUME・NEXT の対象から外れ、結果は「FAILED — playing a demo - press STOP
  first」と出る(機体自身も `/show/load` `/show/run` を 409 で拒否するが、
  PC 側も同じ判定を先にしている)。Units タブでその機体の「Show」行に
  `demo: <名前>` と出ていたら、まず **STOP** を押す(PC 側の進行を止めるだけでなく、
  機体のデモも一緒に終わらせる)。デモが止まった(stopped/ended などデモの
  再生中でなくなった)あとは、その機体は通常どおり監視・補正の対象に戻る
- 同じ名前で再度書き込むと同じ場所へ上書き、違う名前が衝突すると `-2` `-3` と
  ずれる(機体側 `ui/demos.py` の仕様)。1 機体につき保存できるデモは 20 個まで

### 機体側のリモートエージェント(`ui/agent.py`, `ui/remote.py`, `ui/showplay.py`)

`epaper-ui`(`python -m ui.main`)は既定で **TCP 8787 に HTTP エージェント**を立てる
(`--no-remote` で無効、`--remote-port`、`--remote-token TOKEN` で認証必須に)。
標準ライブラリのみで、機体の requirements は変わらない。できるのはパネルの
表示変更だけ(再起動・git pull・FW 更新は不可)。

| エンドポイント | 内容 |
|---|---|
| `GET /status` | ホスト名・コミット・状態・応答基板・直近ログ + 機体の時計 |
| `POST /prepare` | `{"cue","label","dev_type","boards":{"1": 64バイトのhex,…}}` を基板へ保存 |
| `POST /fire` | `{"cue","at"}` — **機体自身の monotonic 時刻 `at`** に表示命令(0x1D ブロードキャスト)を 1 回送る |
| `POST /cancel` `/standby` `/release` | 発火の取り消し / 全面白 / 本体メニューへ戻す |
| `POST /show/load` `/show/preset` | ショーファイルの受け取り / 0:00 の姿を出す |
| `POST /show/run` | `{"t0","show"}` — ショーの 0 秒(機体の monotonic)。START・RESUME・NEXT は全部これ |
| `POST /show/hold` `/show/stop` | 進行の保留 / 終了 |

- PC が各機体の時計のずれを測り(往復の中点、直近 8 回のうち往復が最短の回を採用)、
  「同じ瞬間」を**機体ごとの時計に換算して**渡す。だから命令の到着が遅れても
  発火時刻は揃う。間に合わなかった機体は即発火し、遅れを ms で報告する
- monotonic を使うのは、機体の実時計が timesyncd で飛ぶことがあるため
- PC から操作されると LCD は `REMOTE` 画面になる(ロード済みデザイン、
  保存できた基板数、発火までの秒数 / 発火の遅れ)。**KEY2 で本体メニューへ戻る**。
  `--locked` の機体ではボタンで抜けられない。UPDATE FW・FW VERSION のスキャン・
  REBOOT の実行中は PC からの操作を拒否する(HTTP 409)
- 実測(2026-09-21、radxa-01〜03、実 Wi-Fi、基板は偽バス): 往復 最小 5.6 /
  中央 7.6 ms、ずれの推定のばらつき 0.7 ms / 30 秒、発火は指定の瞬間から
  +0.1〜0.7 ms、3 台の送信時刻の差は 1 ms 未満(推定誤差の上限 ±3 ms は別)

コマンドラインでも同じ検証ができる:

```bash
python -m conductor check   Look22_map.csv Look22_color_pattern01_grid.csv
python -m conductor preview Look22_map.csv Look22_color_pattern01_grid.csv -o p01.png   # 仕上がり
python -m conductor preview Look22_map.csv -o wiring.png     # 配線図(基板の色分け + ソケット番号)
python -m conductor dip     Look22_map.csv -o dip.csv        # DIP スイッチ設定表
python -m conductor arrays  Look22_map.csv GRID.csv -o p01.json
python -m conductor send    Look22_map.csv GRID.csv --only 1 2   # ベンチ: 繋がっている基板へ書く
```

`send` は基板が繋がっている機体で実行する(先に `sudo systemctl stop epaper-ui`)。

## 常時運転(systemd)

常時デモは `epaper-demo.service`(`python -m ui.main --pattern loop
--display null --input none`)として動く。LCD HAT 版 UI と同じコードを
画面なしで走らせているだけなので、演出の追加はどちらにも同時に効く。

`raspi/setup.sh` が `epaper-demo.service` を登録する。既定では
**無効**なので、確認が済んだら有効化する:

```bash
sudo systemctl enable --now epaper-demo   # 電源投入で自動開始
journalctl -u epaper-demo -f              # ログ確認
sudo systemctl stop epaper-demo           # 停止
```

演出のパラメータは `/etc/default/epaper-demo` で変更できる
(サイクル数、間隔など。編集後は `sudo systemctl restart epaper-demo`)。

## ツール(PC版から移植)

| スクリプト | 用途 |
|---|---|
| `host/stop.py` | 再生停止 (0x17)。`--addr N` / `--broadcast` |
| `host/show.py` | 任意パターンの表示(停止→スロット設定→色保存→単張表示) |
| `host/demo.py` | ランダムカラーデモ |
| `host/wave_demo.py` | グラデーション+スパイラル演出(隣接同色なし保証) |
| `host/probe.py` | 疎通診断 |

シリアルポートは STM32 CDC(VID:PID 0483:5740、Linux では `/dev/ttyACM0`)を
自動検出する。手動指定は `--port /dev/ttyACM0`。Pi 内蔵 UART(`/dev/ttyS0`)は
候補から除外されるため、基板が未接続なら「ポートが見つかりません」と
明確に失敗する(誤って内蔵 UART を掴むことはない)。

## 運用上の注意(PC版で実証済みの制約)

- **スロット 17・18 には出荷時のデモ絵が入っている**が、メーカー回答
  (Meris, 2026-09-24, `docs/MERIS_REPLY_3SLOT.md`)によれば全スロットは
  いつでも安全に上書きできる(以前ここに書いていた「0〜18 は書き込み禁止」は
  誤りだった)。本システムの割り当ては **0 = 白のスタンバイ、1〜18 = ショーの絵
  (① Upload の時点で焼き込む)、19 = Designs タブの Prepare とスタンドアロン
  デモの単発表示**(上の「色データは Upload の時点で基板に書き込み済み」と
  `docs/SPECIFICATION.md` §3.3 を参照)
- 色保存(0x13)は毎回フラッシュ書き込みを伴う。常時運転ではサイクル間隔を
  長めに設定する(既定 20 秒、`/etc/default/epaper-demo` で変更可)
- 電源投入時はメーカーのオートプレイが自動再生される。wave_demo は
  開始時のブロードキャスト停止+毎サイクル再送+ガード停止で抑止する
- 基板 ID:2 の ACK は返らない環境がある(コマンド実行はされる)。
  ツールのリトライ・タイムアウトはこの前提で運用する
