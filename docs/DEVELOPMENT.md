# 開発記録 — Raspberry Pi / Radxa 版

2026-08-04 〜 08-09。PC を使わないスタンドアロン運用の実現から、
ファッションショー本番を想定した無停止化・待機状態の定義までの経緯。

判断の背景と「なぜそうしたか」を残すのが目的。**手順は
[README](../README.md)、個別の設計は docs/ の各文書を参照。**

## 1. なぜ Raspberry Pi になったか

当初は M5StickS3(ESP32-S3)からの制御を目指したが、丸 2 日の実機調査の
末に**外部マイコンからパネルを直接制御できない**ことが判明した。

判明した事実(詳細は PC 版リポジトリの docs/DEVELOPMENT.md 8 章):

- 基板間リンクは仕様書の言う RS485 115200 ではなく、
  **3.3V TTL UART 9600bps**(4 ピン = 電源/GND/TX/RX)
  - 電源線は当初 5V と記録したが、実測すると **12V** だった
    (2026-08-09)。**USB からの給電は常に 5V** で、基板上の DC-DC が
    12V に昇圧し、4 ピンはその **12V を基板間で共有するバス**である。
    5V の測定値は昇圧前の値を見ていたものと思われる。
    4 ピンは電力共有が設計意図なので**切ってはいけない**。
    詳細は [SCALING.md](SCALING.md) 4 章
- アドレス 0x01 の基板は**ゲートウェイ**で、上流から来たフレームを
  下流へ中継するが、自分宛のリンク経由コマンドは実行しない
- 中継の実信号を傍受すると、表示コマンドの後に**仕様書に無い 0x1E
  トリガフレーム**を送っており、これが届いて初めてスレーブが動く
- **このシーケンスをバイト単位で完全に再現しても**スレーブは反応しない。
  未文書の条件が残っており、メーカーに問い合わせ中

一方、**PC からの USB CDC 経由の制御は完全な動作実績があった**。
そこで「PC を Raspberry Pi に置き換える」のが最短かつ最確実と判断した。
結果的にこれは正しく、**移植当日に両パネルが動いた**。

## 2. 立ち上げで踏んだ罠

Python コード自体はほぼ無改造で動いたが、足回りで 3 つ躓いた。

**find_port が Pi 内蔵 UART を掴む**
`/dev/ttyS0` が常に存在するため、「ポートが 1 つならそれを使う」という
フォールバックが内蔵 UART を選び、基板未接続時に延々とタイムアウトして
いた。USB CDC/USB シリアルだけを候補にするよう修正。

**gpiozero に lgpio が必要**
無いと gpiozero が実験的な native factory にフォールバックし、
**ボタンの `Button()` が全て EINVAL で失敗**する。HAT 到着後に
「ボタンが効かない」で悩むところだった。requirements に追加。

**systemd でログが出ない**
Python の標準出力がブロックバッファされ、journal に何も届かなかった。
`Environment=PYTHONUNBUFFERED=1` が必須。

## 3. LCD HAT の UI

Waveshare 1.3inch LCD HAT(240x240 ST7789 + ジョイスティック + KEY1〜3)。
**HAT の到着前に開発を終わらせる**ため、表示・入力をバックエンドとして
分離し、PNG 出力とキーボード入力で開発できるようにした。この判断で、
HAT が届いた日には配線確認だけで動いた。

### 性能問題(実測で発覚)

- **RGB565 変換が 1 フレーム 390ms**。再描画間隔 200ms を超えていた。
  `bytes.translate` + `map` で C 側に処理を寄せ 125ms に短縮
- それでも重いので、**内容が変わった時だけ再描画**する方式に変更。
  タイマーは秒単位なのに毎秒 5 回描いていた。入力ポーリングと再描画を
  分離し、ポーリングは 100ms に短縮して操作感を上げた

### HAT の物理競合

同じ Pi に **Waveshare 7.5inch e-Paper HAT**(気象ダッシュボード)が
載っており、**GPIO 24/25 と SPI0 CE0 が完全に衝突**していた。40 ピン
ヘッダも 1 枚しか挿せない。本プロジェクトを優先する判断で、気象
ダッシュボードの cron を**復元可能な形で**(crontab をバックアップし
コメントアウト、アプリ本体は残置)無効化した。

## 4. 演出とタイミング

パターンは WAVE / GRADIENT / SPIRAL / MIRROR / RANDOM / SOLID と、
それらを巡回する Playlist(既定は SOLID 6 色 → RANDOM 6 回)。

**リフレッシュ所要時間を実測した**のが効いた。表示指示のあと停止
コマンドを 0.25 秒間隔で送り続け、ACK が復活するまでを測ると
**色によらず一定で 9.8 秒**。これで:

- 単色デモの切替間隔を **15 秒**に決められた(9.8 秒の描画 + 約 5 秒の静止)
- 「11 秒未満だと絵が落ち着く前に次が来る」と根拠を持って言える
- 引き継いだ `--guard-delay 12` が偶然リフレッシュ完了直後だったと確認できた

パターンごとに間隔を持てるようにし、緩やかな演出と色見本デモで
別のペースを使えるようにした。

## 5. バッテリー耐久試験

**5000mAh のモバイルバッテリーで 7 時間 38 分 27 秒 / 1540 サイクル、
エラーゼロで完走**(残量 0%)。

試験前に気づいた問題が 2 つあり、記録の仕組みを先に用意した:

- **journald が `Storage=volatile`** に設定されており(SD 摩耗対策)、
  ログは全て RAM 上。**電源が落ちれば全消失**する
- **壁時計が信用できない**。RTC が無く、実際に
  「systemd はサービス開始を 8/5 22:43 と記録、アプリの初回ログは
  8/6 10:56」という**約 12 時間のズレ**が起きていた(起動後の NTP 同期で
  時刻が飛ぶ)。タイムスタンプの引き算では経過時間が 3 倍になる

そこで `raspi/runlog.py` を用意した。**uptime とサイクル数だけ**を
60 秒ごとに `fsync` 付きで上書き保存する(追記ではないので容量は一定)。
UI サービスには触れず journal を読むだけなので、**走行中の試験に
後から投入できた**。

停止の有無は**サイクル速度から検証**した。実測 17.82 秒/サイクルに対し
設計値 17.50 秒/サイクル。差は保存とオーバーヘッドで説明でき、
**7 時間半を通じて一度も止まらなかった**と言える(止まって人が再開して
いれば平均値が跳ね上がる)。

電力の分析は [POWER.md](POWER.md)。ここで **パネルの描画電力も Pi の
USB から出ている**という指摘を受け、`lsusb` の `Self Powered` 表示を
根拠にした推論が誤りだったと訂正した。**USB ディスクリプタは
ファームウェアの自己申告であり、配線の証拠にはならない。**
リフレッシュのデューティ比が 55% と高いため、**更新間隔を延ばすことが
最大の省電力策**という結論に変わった。

## 6. 無停止化(ショー運用)

ファッションショーで使うと決まり、要件が「止まらないこと」に変わった。

**問題**: 1 回の ACK 欠落でワーカースレッドが終了し、パネルが固まって
ボタンを押すまで復帰しなかった。しかもこれは**実際に起きていた** —
電源投入直後、メーカーのオートプレイでパネルがリフレッシュ中(9.8 秒は
無応答)のときに停止コマンドを送って失敗していた。**正常な一過性事象で
止まっていた**わけである。

**対策**(設計は [RELIABILITY.md](RELIABILITY.md)):

- コマンドは指数バックオフで再試行。**リフレッシュ 2 回分を跨げる長さ**
- それでも駄目なら**そのサイクルだけ諦めて次へ**。次回はスロット設定から
  やり直す(基板が再起動していても復帰する)
- シリアル例外や連続失敗で**`find_port()` からバスを開き直す**
  (USB 再列挙でデバイス名が変わるため)
- ポートが無ければ待ち続ける。**ワーカーは停止要求以外では終了しない**
- 色保存だけは再試行を絞る(毎回フラッシュ書き込みが走るため)
- ~~**表示コマンドを 3 回送る**~~ → **1 回だけ送る**(`SHOW_REPEATS = 1`)。
  「リフレッシュ中の基板は無視するので冪等」は**誤り**だった。基板は
  リフレッシュ中に届いたコマンドを**捨てず受信バッファに溜め、描き
  終わってから実行する**ので、余分な 1 通が丸ごと 1 回分の再描画になる。
  実機実測(2026-08-14):3 通送ると 1 番基板が 2 回描き直して 34 秒、
  20 番基板は 35 秒で終了。1 通なら両基板が揃って描く
  (無応答 0.7〜17.1 秒/1.2〜17.3 秒)。「基板ごとのズレ」の正体はこれ

**着弾確認付き送信(2026-09-26 追加)**。上記のとおり表示は 1 通の
非応答ブロードキャストなので、**取りこぼしても誰も気づかない** ―
radxa-04 の LOOK26 リハーサルで、最後のキューが `fired (+166 ms)` と
記録されたまま基板が変わらなかった(その機体の USB は
`usb1-port1: disabled by hub (EMI?)`、ショー中に ttyACM0→ttyACM1 の
再列挙あり)。デモループなら次のサイクルが直すが、ショーのキューに
「次のサイクル」は無い。そこで:

- 発火の **1.5 秒後**(`ui/runner.py` の `VERIFY_AFTER_S`。立会い基板の
  スイープ開始からの 1.5 秒)、**立会い基板 1 枚**に読み取り専用の
  `0x02`(バージョン取得)を投げる。**読むのは答えの中身ではなく
  沈黙**:再描画中の基板は何も返さないので、無応答か `ACK_BUSY` なら
  「届いた」。**何か答えたなら描いていない**=そのキューは届いて
  いない(製品 FW は 0x02 に `ACK_FAIL 0x0A` を返す ―
  [SPECIFICATION.md](SPECIFICATION.md) 5.5。拒否も立派な「答え」)。
  1.0 秒ではなく 1.5 秒なのは、2026-08-14 の実測で**遅いほうの基板が
  +1.2 秒でもまだ応答していた**ため ― 無応答になる前に聞けば
  「idle」と読んで無駄な二度描きになる
- **質問は 2 回**(`VERIFY_TRIES`、読み取り 0.3 秒 × 2 = 0.6 秒)。
  このリンクは**送信方向も落とす**ので、届かなかった質問が
  「無応答=届いた」に化けると、まさに拾いたい故障を緑で報告して
  しまう。2 回とも沈黙して初めて「届いた」。なお**次のトリガまで
  0.6 秒を切っていたら質問そのものを始めない**(始めればその分だけ
  次キューが遅れる)― `verify skipped: cue Y is due`
- 届いていないと判った時だけ、**もう 1 通だけ**送り直す。**1 回の
  発火につきブロードキャストは最大 2 通**(3 通目は上記 2026-08-14 の
  二度描きそのもの)。送り直す直前に**停止と次キューをもう一度見る**
  ― 質問に 0.6 秒かかるので、その間に事情が変わりうる
- **送り直す/送り直さないの判定は「次キューをどれだけ遅らせるか」**
  (`REPAIR_LATE_S = 2.0` 秒)。基板は再描画中に届いたコマンドを
  捨てずに溜めて後で実行するので、修復が次のトリガまで残っていても
  **同じスロットを二度描くのではなく、次の絵がその分遅れる**。
  式は `now + refresh_s + span_s ≤ 次キューの発火時刻 + 2 秒`。
  9 秒間隔・リフレッシュ 7 秒なら、span 1 秒のキューは T+2.5 に
  「届いていない」と判って T+10.5 に描き終わる(次キューは 1.5 秒
  遅れ)ので**送り直す**。span 7 秒は T+8.5 に判って T+22.5 ―
  11.5 秒遅れなので**送り直さない**
- **送り直さないと決めた場合も「不明」ではなく「損失」として扱う**:
  `landed = "idle-not-repaired"`、ログは
  `cue X not applied at @01 (checked +N s), not re-sent: cue Y due in M s`、
  Conductor のタイルは**赤の「not applied」**。届いていないと判った
  ものを「何も表示しない」で済ませてはならない。2 通目でも確認
  できなければ `cue X re-send unconfirmed @NN` で同じく赤
- 赤い判定は `show-run.json` に保存されるので**再起動しても消えない**
  (実機がまだ間違った絵のままなのだから)。再開して RUNNING に戻った
  ショーでは数秒後に次キューの判定が上書きするので、これが効くのは
  **最後のキューで止まった/HOLD/LOADED のまま再起動した場合**
- 遅れて参加した基板のための**再送(heal、`ui/showplay.py`)は
  確認しない** ― そのキューは一度「届いた」と確認済みで、今回の
  1 通はそもそも聞く相手がいなかった基板のためのものだから。
  heal で増えるのはちょうど 1 通
- 立会い基板は**既定で USB 直結基板(アドレス 1)だけ**
  (`--verify-witness usb`)。**485 中継越しの照会は安全が未確認**
  だからである ― 0x29 は中継すると無応答のうえ USB 側 CDC が電源
  再投入まで固まる([SPECIFICATION.md](SPECIFICATION.md) 5.7)。
  0x02 でそれを試した記録は無い。**ショー中にマスタが固まるのは、
  1 通落ちるより悪い**。アドレス 1 が生きていなければ
  `verify skipped: usb board absent` として何も聞かない
- 待ち時間は**その基板自身の最初のソケット開始時刻**から数える。
  スイープが garment の中央から始まる場合、アドレス 1 の出番は数秒後
  なので**確認も数秒後**になる ― それで良い(ログの
  `checked +3.6 s` がその実測値)。スイープ表を機体が知らないキューは
  **確認せずスキップ**(早すぎる質問は「idle」と誤読して 1 回分の
  再描画を無駄に増やす)。開始が**キューの span を超える**表(16bit
  フレームなので壊れた 1 エントリが 655 秒に読める)や、span の申告が
  無いまま `VERIFY_MAX_DELAY_S`(30 秒)を超える表も同様にスキップ ―
  何分も待つ間、再プローブもガード停止も止まってしまう
- `--verify-witness any`(**スイープ開始が最も早い生きた基板**を聞く。
  立会いとしては最強)は、**下記のベンチ試験で「中継した 0x02 が
  マスタを固めない」ことを確認してから**にすること:
  1. 基板 2 枚を実機構成で接続(ID:1 を USB、ID:2 を 485 の先)
  2. `host/probe.py` の要領で **ID:2 宛の 0x02** を送る(応答の有無は
     どちらでもよい)
  3. 直後に **ID:1 宛の 0x17 が ACK を返すか**を見る。返らない/
     Write timeout なら CDC が固まっている = `any` は使えない。
     5.7 の再現と同じ手順で、そのときは電源再投入が必要
  4. 10 回繰り返して 1 度も固まらないことを確認する
- **前提**:基板は表示コマンドの 0.7〜1.2 秒後から描き終わりまで
  無応答(2026-08-14 実測。2 枚で 0.7 秒と 1.2 秒)。
  **基板の型が変わったら、下げる前に必ず再測定すること** ―
  `--verify-after` を 0.2 秒刻みで振り、`landed (@NN deaf)` に変わる
  境目が新しい無応答開始時刻。既定の 1.5 秒はそれより十分後ろに置く
  (上側は再描画 16 秒までいくらでも安全)。確認そのものを止めるなら
  `--no-verify-fire`

**ショー中の基板一覧は PC のものが絶対(2026-09-26 リハ)**。機体は
`--boards` が無ければ自分でバスを探索する(1 から上へ、最後に応答した
基板の先 `EXPLORE_GAP` = 6 個が続けて無応答なら打ち切り)。radxa-04 は
スタンバイで起動したため探索が走り、`board 17-22 absent, skipping` と
記録した ― そこまでは正しい。問題はその後で、ショー(16 枚)の基板一覧が
届いても 17-22 が `absent` に残り、`_reprobe()` が 60 秒ごとに存在しない
6 枚を叩き続けた(1 枚あたりシリアルタイムアウト約 1.5 秒 = 1 回 15 秒)。
そのプローブの最中にトリガが来たキューは +492 / +246 / +73 ms 遅れて
発火した(同じショーで、最初から REMOTE に入って一覧を持っていた
radxa-05 は `absent` 空・プローブ無し・+1 ms)。

- **ジョブ(ショーの焼き込み / `/prepare`)が基板一覧を持ってきたら、
  それが唯一の一覧**になる(`ui/runner.py` の `_apply_job_boards()`):
  `boards` を差し替え、`absent` と `live` を一覧の中だけに絞り、探索を
  止め、フレームの group_count も一覧に追従させる。ログは 1 行
  `boards 1-16 from the show (17-22 dropped, not probed)`
- 一覧の中の**無応答の基板は今までどおり再プローブされる**(あとから
  電源が入った基板はショーに参加できなければならない)。一覧の外は
  応答しても無視する ― 存在しない基板への通信はショー中のバスの雑音
- **KEY2 / release で機体の menu に戻ったら**、起動時の設定どおりの
  探索に戻る(`the show's board list is released, exploring again`)
- **ショーの途中で再起動した機体**も同じ規則に入る。
  `ShowPlayer.restore()` は焼き直さない(仕様どおり)ので基板一覧を運ぶ
  ジョブが来ない ― radxa-04 のリハはおそらくこの経路だった。PC から
  新しく送るものは無く、**機体のショーファイル自身が一覧を持っている**
  (`conductor/showfile.py` の `boards`)ので、`ShowPlayer` が
  **`RemoteSession.set_boards()`** で渡す:`restore()`(ショーがどの状態で
  戻ってきても)と `load()`(焼き込みの前、かつ独立に ― 全ペアがキャッシュに
  当たって何も書かない焼き込みでも一覧は効く)。デモも同じ道。ワーカーは
  `_run_remote()` の頭でジョブと同じように拾う。
  **`set_boards()` は `wake()` しない** ― 立てっぱなしのイベントは遅れた
  キューの発火時刻を待つ `ARM_GRACE_S` に食われ、復帰したショーが探索の
  **後**に絵を出すようになる(`tests/test_showplay.py` が押さえている)

テストは**障害注入**で「止まらないこと」を固定した
(`tests/test_ui_resilience.py`)。恒久障害・シリアル例外・ポート消失・
20% ランダム障害のいずれでも `runner.running` が False にならないことを
検証する。

## 7. 運用のための作り込み

**ボタンロック(`--locked`)**: 本番で KEY1 に触れるとデモが止まる。
ロック中は全ボタン無効、解除は KEY2→KEY3→KEY2、**1 分の無操作で自動
再ロック**(掛け直しを忘れても安全)。ロック中でも画面は点灯できる。

**KEY1 の意味を変更**: 開始 → 一時停止 → 再開。1 秒長押しでリセット。
一時停止はサイクル数とタイマーを保持し、**停止していた時間は経過時間に
加算しない**。長押しと短押しが二重発火しないよう、長押しは押下中に発火して
その押下を消費済みにしている。

**バックライト**: KEY3 で手動消灯。自動消灯は実装したが**既定はオフ**
(暗い画面は「壊れた」に見えるため)。バッテリー運用時に
`--blank-after 10` で有効化する。

**復帰不能を作らない**: KEY3 が当初「終了」だったため、押すと画面が
消えたまま戻らなくなった(正常終了は `Restart=on-failure` の対象外)。
**画面が唯一の操作手段の機器で、ボタン操作により SSH なしには復帰
できない状態を作れてはならない**という原則を立て、KEY3 をスリープに
変更し `Restart=always` にした。

**ウォッチドッグ**: `Type=notify` + `WatchdogSec=120`。クラッシュでは
なく**ハング**した場合も自動再起動される。実機で 160 秒経過しても
再起動カウンタが 0 のままであることを確認済み。

## 8. Radxa Cubie A7Z への移植

Pi Zero 2 W が欠品・価格高騰したため、代替機として同じシステムを載せた。
先に [PORTING.md](PORTING.md) で可否だけを判断し、その通りに実施している。

**移植可能と判断した根拠**: パネル制御は USB CDC なので基板に依存しない。
ボード依存は LCD HAT の SPI と GPIO **だけ**だった。

**やったこと**:

- ピン配置と GPIO バックエンドを `ui/boards.py` の**プロファイル**に
  切り出し、`/proc/device-tree/compatible` で自動判別する
- Pi の `gpiozero`(lgpio)は 1GB の A7Z ではビルドが 10 分以上かかり
  SSH が落ちた。**キャラクタデバイスを直接叩く `python-periphery`** に
  変更し、要件ファイルを `raspi/` と `radxa/` に分けた
- Radxa の GPIO 番号は `32×バンク + n`(chip0: PA〜PK、chip1: PL/PM)
- Debian 11 の **Python 3.9** で動くよう全 18 ファイルに
  `from __future__ import annotations` を追加(`dict[int,int] | None` 対策)

**踏んだ罠**:

- Wi-Fi 接続がユーザーセッションに紐付いており、**reboot でネットワーク
  ごと消えた**。`connection.permissions ""` + 自動接続で解消
- `journalctl` が空 → ユーザーが `adm` グループに未所属だった
- `sudo` のパスワードレス化で書き損じ、`visudo -cf` で検証してから
  壊れたファイルを消す手順に変更

実機で 132 件のテスト、GPIO 11 本、ボタン 9 イベント(長押し含む)、
LCD(初期化 370ms / フレーム 107〜142ms)、両基板の ACK、reboot 後の
自動起動まで確認済み。手順は [radxa/README.md](../radxa/README.md)。

## 9. 待機状態の定義(全面白)

**問題**: パネル基板は**電源投入だけでメーカーのデモを自動再生し始める**。
そのため「何もしていない状態」がショーの背景として使えない映像になり、
かつホストがハングしているのか正常に待機しているのかも区別できなかった。

**決定**: ホストが基板との接続を確立した時点を境に、**全セクター白で
停止**を待機状態と定義する。デモを選ぶ前の状態が常に白になる。

**実装で分かった要点**: 白を保存して表示させるだけでは足りない。
スロットを表示させると基板は「再生中」のままなので、**9.8 秒の
リフレッシュが終わった後そのままメーカーデモへ流れ込む**。
ループデモが毎サイクル `_wait_next` でやっているのと同じ処置
—— ガード時間(既定 12 秒)後にもう一度停止指令 —— を、1 回きりの
待機描画にも入れて解決した。

再試行は 6 章の層をそのまま使う。実機では**毎回**、電源投入直後の
基板 ID:1 がリフレッシュ中で無応答になり、4 回目の再試行で ACK して
白に落ち着いた —— つまり**リトライ無しでは成立しない**機能である。

**追加で分かったこと(USB 抜き差し)**: 待機を「起動時に 1 回」で作ると
不十分だった。**USB を抜き差しすると基板の電源が切れ、メーカーデモを
再生しながら復帰する**。基板側からは何も通知が来ないため、待機中は
デバイスノードを 2 秒ごとに見張り、変化したら白を描き直す。

見張る対象は**存在ではなく同一性**(inode + ctime)にした。存在確認だけだと
ポーリングの隙間で完結した速い抜き差しを取りこぼすが、再列挙では
devtmpfs のノードが作り直されるため名前が同じでも別物として検知できる。
さらに検知漏れの保険として、待機中は 60 秒ごとにブロードキャスト停止を
送る(8 バイト 1 フレーム。壁の見た目を壊すのはオートプレイの再生なので、
そこだけは止める)。

**PC がショーを回している最中も同じ 60 秒**(`REMOTE_GUARD_S`、
`--remote-guard 秒`、0 で無効。2026-09-27)。REMOTE には発火後のガード
(`--guard-delay`、`_guard_for()` で伸びる)しか無く、キューの間隔が空くと
バスが数十秒無音になる。そこでオートプレイを勝手に再開した基板が
リフレッシュに入り、次のキューの書き込みをブロックして落とした
(STATUS.md 2 章)。送るのは**ワーカが暇で、直前の show から
`_guard_for()` 秒経っていて、次のキューまで 5 秒(`REMOTE_GUARD_HOLD_S`)
以上あり、prepare / burn が待っていない時だけ**。ブロードキャスト 0x17 は
どれでもタイマをリセットするので、起動時の停止や発火後のガードの直後に
余計な 1 発は出ない。

つまりランナのタイマは 4 本 ―― `--interval`(デモの周期)、
`--guard-delay`(発火・サイクル後のガード停止)、`LINK_GUARD_S`(待機中の
60 秒)、`REMOTE_GUARD_S`(REMOTE 中の 60 秒)。ほかに `LINK_POLL_S`
(2 秒、デバイスノードの見張り)と `REPROBE_INTERVAL_S`(60 秒、不在基板の
再探索)。

併せて、`ui/main.py` が起動時に検出したポート名を**固定して**ランナに
渡していたのをやめた。再列挙で `ttyACM0` → `ttyACM1` に変わると
二度と見つからなくなるため。ランナは元々開き直すたびに `find_port()` を
呼ぶ設計で、固定がそれを打ち消していた。

**監視するのは待機中だけ**とした(承認済みの割り切り)。デモ実行中の
抜き差しはバスを開き直して次のサイクルで描き直されるので既存の層で足りる。
**一時停止中だけは次のサイクルが来ない**ため、KEY1 で再開するまで
メーカーデモが流れたままになる。一時停止は「今の表示を保持する」状態で
何を描き直すべきかを持っておらず、そこを直すと保持の意味が変わるため、
現仕様のままとした。

白のままにしたくない場合は `--no-standby`。

副次的に、待機はブート直後からポートを待つため、パネル未接続のホストで
「no serial port, waiting」が 10 秒ごとに出続けた(1 日約 8600 行)。
1 回だけ出す形に変更した。

#### ビルドの 2 系統(音源入り / 音源なし)

`build_designer.py` の出力は 2 つあり、**コミットされるのは音源なしの
`dist/az27ss-simulator.html` だけ**(2 MB の上限も `--check` もこちらだけの話)。

| | 何が入るか | どう作るか | 置き場所 |
|---|---|---|---|
| **lean(コミット版)** | 音源なし。約 560 KB | `python tools/build_designer.py` | `dist/az27ss-simulator.html`(コミットする) |
| **音源入り(配布版)** | ショーの音源を base64 で埋め込み。17.5 MB の MP3 で約 23 MB | 通常は **Conductor の Timeline タブの「Simulator for designers…」ボタン**(`GET /api/simulator?music=1`、サーバ内で `build_page()` を呼ぶ)。手元で作るなら `python tools/build_designer.py --music auto`(`./showdata` の `show.json` が指す音源。`--workspace` で変更可、`--music PATH` で直接指定も可) | `dist/az27ss-simulator-with-music.html`(**.gitignore 済み。絶対にコミットしない**) |

- 埋め込みは `SIM.embeddedMusic = {name, type, size, dataUrl}` という `<script>` 1 個で、
  他のモジュールより**前**に出る(dev ページの `defer` でも、ビルド版のインライン順でも、
  `designer-app.js` の `boot()` が動く時点で必ず居るようにするため)。ページ側は起動時に
  1 度だけ Blob 化して object URL を作り、base64 文字列は捨てる(designer-app.js の
  `builtInMusicUrl()`)。**音源は再エンコードしない**(このマシンに ffmpeg は無いし、
  ショーのマスターを勝手に作り直すのはこのスクリプトの仕事ではない)
- `check_self_contained()` は `data:` URL を通し、`http(s)://`・プロトコル相対 `//`・
  `@import`・`<link>` だけを弾く
- **生成した音源スクリプトも、他のモジュールと同じエスケープ(`_escape_script_hazards` +
  制御文字チェック)を通す。ただし base64 本体だけは対象外**(文字種が `A-Za-z0-9+/=` で
  `<` も制御文字も原理的に含まれないので、23 MB に正規表現を 3 回かけても何も見つからない)
- **ファイル名は JSON + `<` でエスケープ、MIME は「エスケープではなく検証」**:
  MIME は `data:` URL の中に生の文字列として入る(直後の `;base64,` は URL 構文であって
  文字列ではないので、引用もエスケープもできない)。`show.json` は人が手で直せるファイルで、
  `type` に `audio/mpeg";x="` と書けば `dataUrl` のリテラルを閉じて後続がコードになる。
  そのため `safe_mime()` が `type/subtype`(RFC 9110 の token 文字のみ)に
  合致しないものを弾き、拡張子から引いた MIME に差し替える(ビルドは失敗させない
  ―― オペレーターの打ち間違いで配布物が作れなくなる方が困るし、拡張子の方が当てになる)
- **音源が変わったときの手順は「ボタンをもう 1 回押す」だけ**。開発者を呼ぶ必要は無い
  (2 回目以降のクリックは、音源の 名前/サイズ/`st_mtime_ns`/先頭・末尾 64 KB のダイジェストを
  キーにしたキャッシュから即座に返る。`int(st_mtime)` では、同名・同サイズの差し替えが
  同じ秒内に起きると古い音源を配ってしまう)
- **音源を変えた直後の 1 回だけ、オペレーターの画面が 1.6 秒ほど固まる**:
  ビルドは Python の CPU 処理で、その間 GIL を握るため `/api/state` のポーリングが待たされる。
  ボタンを押したときのトーストはそのための予告でもある。2 回目以降はキャッシュなので止まらない

3 つとも `--check` モードで「コミットされているものと同じか」を確認できる
(`tests/test_sim_goldens.py::test_goldens_are_current`、
`tests/test_designer_build.py::test_build_is_current`)。**生成物を手で直接編集しない**
