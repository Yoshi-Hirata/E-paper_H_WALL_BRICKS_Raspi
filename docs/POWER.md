# 待機電力の削減手法(検討メモ)

作成: 2026-08-06。ロングランテスト中のため**実機への適用は保留**、手法の整理のみ。

## 1. 先に結論

- **削れるのは概ね半分まで**。全部やっても Pi Zero 2 W の下限は
  **80〜100mA(0.4〜0.5W)程度**で、ここから下がらない
- 理由: **Raspberry Pi はサスペンド(suspend-to-RAM)に対応していない**。
  15〜60 秒の指令の合間に「深い休止」へ入る手段が無く、常にフル稼働の
  アイドル状態を維持し続ける
- 効果が大きい順に **LCD バックライト → HDMI → Wi-Fi → CPU クロック**。
  このうち Wi-Fi は SSH 保守を失うので**非推奨**
- **桁で下げたいならアーキテクチャの話**になる(→ 5 章)

## 2. 現状の内訳(推定)

公開されている実測値には幅があるため、**自分で測ることが前提**。

| 要素 | 目安 | 備考 |
|---|---|---|
| Pi Zero 2 W 本体アイドル | 100〜160mA | 構成により差が大きい |
| HDMI 出力 | 20〜30mA | **ヘッドレス運用なので完全に無駄** |
| Wi-Fi | 30〜50mA | SSH 保守に必要 |
| LCD バックライト | 20〜40mA(要実測) | 常時点灯なら効く |
| 我々のプログラム | ほぼ 0 | 待機中は sleep。CPU は使っていない |

参考値: ヘッドレス + Wi-Fi/BT 無効で約 114mA、Wi-Fi 有効のまま
HDMI と v3d を無効にして約 77mA という報告がある。

## 3. 手法(効果とリスク)

### A. 効果が大きく、リスクが低い(推奨)

**A-1. LCD の自動消灯(オートブランク)** — 20〜40mA
一定時間ボタン操作が無ければ自動でスリープへ。**既に KEY3 のスリープ機構
(`display.sleep()/wake()`)があるので、タイマーを足すだけ**で実装は小さい。
デモは裏で動き続け、どのボタンでも復帰する現在の挙動をそのまま使える。
発展: バックライトをソフト PWM で調光すれば「薄暗く点灯」も可能。

**A-2. HDMI / 映像出力の無効化** — 20〜30mA
ヘッドレス運用なので純粋な無駄。`/boot/firmware/config.txt` での無効化、
または起動時に一度コマンドを打つ方式。

**A-3. ACT LED の消灯** — 数 mA
`/sys/class/leds` の trigger を none にして brightness 0。

**A-4. 不要サービスの停止** — 数 mA
Bluetooth(Zero 2 W は搭載)、avahi、triggerhappy、ModemManager など。

### B. 効果はあるが副作用に注意

**B-1. CPU ガバナ / クロック上限** — 10〜20mA
`powersave` 固定や `arm_freq` の引き下げ。ただし**描画がバースト処理**
(RGB565 変換に 125ms)なので、UI の反応が鈍くなる副作用がある。
自動消灯と併用するなら、そもそも描画しない時間が増えるので効果は薄い。

**B-2. UI のポーリング間隔** — 数 mA 以下
現状 0.1 秒間隔。ボタンは割り込み駆動でキューに入るため、待機中は
より長くブロックしても取りこぼさない。CPU が深いアイドルに入りやすく
なるが、**効果は小さい**割に実装は要注意(タイマー表示との整合)。

### C. 非推奨

**C-1. Wi-Fi の停止** — 30〜50mA
効果は大きいが**SSH による遠隔保守を失う**。今回の開発で分かったとおり、
遠隔でログを見られることの価値は大きい。どうしてもやるなら
「展示モード時のみ無効化 + 物理ボタン長押しで復帰」のような
戻り道を用意すること。

**C-2. デモ周期を延ばす** — ほぼ効果なし
Pi 側の処理は 1 サイクル数百 ms しかなく、待機時間が伸びるだけ。
パネルのリフレッシュ電力はパネル側の電源から出ており Pi とは無関係。
(フラッシュ書き込み回数を減らす意味はあるが、電力の話ではない)

## 4. 測定方法

**変更は 1 つずつ、同条件で比較する。** まとめて適用すると効果が分からない。

1. USB 電力計を Pi の電源ラインに入れる
2. 条件を揃えて測る: ①デモ実行中(パネル更新の瞬間)②サイクル間の待機中
   ③LCD 消灯時。待機中の値が今回の主対象
3. 変更 → 再起動 → 同じ 3 条件を測る

## 5. 桁で下げたい場合(アーキテクチャの話)

「もっと下げたい」の答えは**ホストを止めること**だが、本システムでは
構造的な制約がある。

- **ESP32 に替えても解決しない**。ESP32 の deep sleep は数十 µA だが、
  それは USB ホストを維持できない状態。パネルへ指令を出し続けるなら
  起きている必要があり、結局同じ壁に当たる
- **本当の低電力化はパネルの自律再生を使うこと**。プロトコルには
  再生開始(0x16、開始スロット + 間隔秒)があり、これを使えば
  ホストの電源を切っても**パネル単体でループ再生**できる。
  ただし**書き込めるのはスロット 19 のみ**(0〜18 はメーカーデータで
  書き込み禁止)なので、**自前の絵を複数枚ループさせることは現状できない**
- 例外: **表示内容がメーカーのデモで良いなら、ホストは完全に不要**。
  電源投入時のオートプレイがそれであり、この場合の待機電力はゼロ

つまり「自前の演出を流し続けたい」という要件がある限り、
ホストは起きているしかない。→ **0.4〜0.5W が現実的な下限**。

## 6. 進め方の提案

1. ロングランテスト完了を待つ
2. **まず A-2(HDMI)・A-3(LED)・A-4(サービス)を適用**。
   我々のコードに触れずに済み、リスクが低い。ここで一度測定
3. 次に **A-1(LCD 自動消灯)を実装**。コードに触れるのはここだけ。
   消灯までの時間は設定可能にする(既定 5 分など)
4. 測定結果を見て、B-1(クロック)まで踏み込むか判断
5. Wi-Fi(C-1)は触らない

**費用対効果の確認を先に**: 常時給電の展示用途なら、0.5W の削減は
年間で数十円程度。バッテリー運用や多数台展開でなければ、
労力に見合わない可能性がある。目的(電気代 / 発熱 / バッテリー持ち)を
はっきりさせてから着手するのが良い。
