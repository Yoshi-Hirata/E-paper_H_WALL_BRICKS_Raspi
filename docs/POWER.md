# 待機電力の削減手法(検討メモ)

作成: 2026-08-06。ロングランテスト中のため**実機への適用は保留**、手法の整理のみ。

## 1. 先に結論

- **実測の平均消費は 300〜370mA(1.6〜1.8W)**(2 章、5000mAh で 7.6 時間)
- **最も効くのは更新間隔を延ばすこと**(3 章 D)。パネルの描画電力は
  Pi の USB から出ており、リフレッシュに全時間の 55% を費やしているため。
  間隔を 2 倍にするだけで約 18% 削減でき、他の対策の合計より大きい
- 次いで LCD 自動消灯・HDMI 無効化(3 章 A 群、合計 約 80mA)
- **Pi 自体の下限は 80〜100mA(0.4〜0.5W)程度**で、ここから下がらない
- 理由: **Raspberry Pi はサスペンド(suspend-to-RAM)に対応していない**。
  15〜60 秒の指令の合間に「深い休止」へ入る手段が無く、常にフル稼働の
  アイドル状態を維持し続ける
- 効果が大きい順に **LCD バックライト → HDMI → Wi-Fi → CPU クロック**。
  このうち Wi-Fi は SSH 保守を失うので**非推奨**
- **桁で下げたいならアーキテクチャの話**になる(→ 5 章)

## 2. 実測値(2026-08-06 バッテリー完全放電試験)

**5000mAh のモバイルバッテリーで 7 時間 38 分 27 秒 / 1540 サイクル**動作し、
残量 0% で終了した(完全放電を確認)。ここから平均消費を逆算する。

| 前提(バッテリーの実効容量) | 平均消費 |
|---|---|
| 公称 5000mAh @3.7V = 18.5Wh をそのまま | 2.42W(484mA @5V) |
| 実効 75%(13.9Wh) | 1.82W(**364mA**) |
| 実効 65%(12.0Wh) | 1.57W(**314mA**) |

モバイルバッテリーは昇圧損失などで公称の 65〜75% 程度しか出せないのが
一般的なので、**平均 300〜370mA(1.6〜1.8W)**と見るのが妥当。

### パネルの描画電力も Pi から出ている(重要)

**電子ペーパーの描画電力は Pi の USB から供給されている**(配線として確認済み)。

注意: `lsusb -v` は制御基板を **Self Powered / MaxPower 100mA** と報告するが、
これは**ファームウェアが申告している値にすぎず、実配線とは一致していない**。
USB ディスクリプタを電源構成の根拠に使ってはいけない。

この事実が効くのは**デューティ比**が高いため:

```
リフレッシュ 9.8 秒 ÷ 平均サイクル 17.8 秒 = 稼働時間の約 55%
```

**試験中、パネルは半分以上の時間リフレッシュしていた**。しかも 2 枚同時。

### 内訳の推定(実測 330mA 前後を分解)

| 要素 | 目安 | 備考 |
|---|---|---|
| Pi Zero 2 W 本体アイドル | 100〜160mA | 構成により差が大きい |
| **パネル 2 枚(平均)** | **130〜180mA** | 逆算値。リフレッシュ中はこの倍近い |
| Wi-Fi | 30〜50mA | SSH 保守に必要 |
| HDMI 出力 | 20〜30mA | **ヘッドレス運用なので完全に無駄** |
| LCD バックライト | 20〜40mA | **試験中は常時点灯していた** |
| 周期処理(描画・シリアル) | 10〜30mA | 1 秒ごとの再描画 |

**当初の見積り(0.5W 程度)は 3 倍以上楽観的だった。**
最大の誤りはパネルの電力を勘定に入れていなかったこと。

### バッテリー容量と稼働時間の目安(実測からの線形換算)

| 容量 | 現状のまま | 3 章 A 群を適用(約 −80mA)|
|---|---|---|
| 5000mAh | **7.6 時間(実測)** | 約 10 時間 |
| 10000mAh | 約 15 時間 | 約 20 時間 |
| 20000mAh | 約 30 時間 | 約 40 時間 |

## 3. 手法(効果とリスク)

### A. 効果が大きく、リスクが低い(推奨)

**A-1. LCD の自動消灯(オートブランク)** — 20〜40mA
一定時間ボタン操作が無ければ自動でスリープへ。**既に KEY3 のスリープ機構
(`display.sleep()/wake()`)があるので、タイマーを足すだけ**で実装は小さい。
デモは裏で動き続け、どのボタンでも復帰する現在の挙動をそのまま使える。
発展: バックライトをソフト PWM で調光すれば「薄暗く点灯」も可能。

**A-2. HDMI / 映像出力の無効化** — 20〜30mA
ヘッドレス運用なので純粋な無駄。`/boot/firmware/config.txt` での無効化、
または起動時に一度コマンドを打つ方式。

**A-3. ACT LED の消灯** — 数 mA
`/sys/class/leds` の trigger を none にして brightness 0。

**A-4. 不要サービスの停止** — 数 mA
Bluetooth(Zero 2 W は搭載)、avahi、triggerhappy、ModemManager など。

### B. 効果はあるが副作用に注意

**B-1. CPU ガバナ / クロック上限** — 10〜20mA
`powersave` 固定や `arm_freq` の引き下げ。ただし**描画がバースト処理**
(RGB565 変換に 125ms)なので、UI の反応が鈍くなる副作用がある。
自動消灯と併用するなら、そもそも描画しない時間が増えるので効果は薄い。

**B-2. UI のポーリング間隔** — 数 mA 以下
現状 0.1 秒間隔。ボタンは割り込み駆動でキューに入るため、待機中は
より長くブロックしても取りこぼさない。CPU が深いアイドルに入りやすく
なるが、**効果は小さい**割に実装は要注意(タイマー表示との整合)。

### C. 非推奨

**C-1. Wi-Fi の停止** — 30〜50mA
効果は大きいが**SSH による遠隔保守を失う**。今回の開発で分かったとおり、
遠隔でログを見られることの価値は大きい。どうしてもやるなら
「展示モード時のみ無効化 + 物理ボタン長押しで復帰」のような
戻り道を用意すること。

### D. 最も効く対策: 更新間隔を延ばす

**当初これを「ほぼ効果なし」と書いていたのは誤り**だった。パネルの描画電力が
Pi から出ている以上、**リフレッシュのデューティ比がそのまま電力に効く**。

現状は 1 サイクル平均 17.8 秒に対しリフレッシュ 9.8 秒 = **デューティ 55%**。

| 平均サイクル間隔 | リフレッシュ比率 | パネル平均電流(推定)| 総電流(推定)|
|---|---|---|---|
| 17.8 秒(現状) | 55% | 130〜180mA | 約 330mA |
| 30 秒 | 33% | 80〜110mA | 約 270mA |
| 60 秒 | 16% | 40〜55mA | 約 230mA |
| 120 秒 | 8% | 20〜28mA | 約 210mA |

間隔を 2 倍にするだけで **60mA 前後(約 18%)** 削減でき、
これは HDMI + LED + サービス停止を全部足したより大きい。
**フラッシュ書き込み回数も同時に減る**ため、寿命の面でも有利。

演出としての見栄えとのトレードオフになるが、**ショー本番以外の
待機時間帯だけ間隔を延ばす**といった使い分けが現実的。

## 3.5 バッテリー耐久試験の記録(実装済み)

モバイルバッテリー運用では**電源が落ちて終わる**ため、停止時に何かを
保存する仕組みは原理的に作れない。**動作中に書き続けておく**しかない。

### この Pi で判明した罠

1. **journald は `Storage=volatile`** に設定されている(SD 摩耗対策と思われる)。
   ログは全て RAM 上にあり、**電源断で全消失する**。`journalctl --flush` は
   仕様上 no-op なので効かない
2. **壁時計が信用できない**。RTC が無く、実際にこの機体で
   「systemd はサービス開始を 8/5 22:43 と記録、アプリの初回ログは
   8/6 10:56」という**約 12 時間のズレ**が起きていた(起動後に NTP が
   同期して時刻が飛んだ)。タイムスタンプの引き算では経過時間が 3 倍に
   なる。**経過時間は `/proc/uptime` を使う**

### 対策: `raspi/runlog.py`

必要な数値だけを 60 秒ごとに追記する常駐プロセス。journald には手を
入れない(SD 摩耗対策の意図を尊重し、書き込みは 1 分あたり数十バイト)。

- 出力: `~/runlog/epaper-run.csv`(履歴)と `~/runlog/latest.txt`(最新値)
- 記録項目: 壁時計 / **uptime(秒・HMS)** / サイクル数 / パターン /
  **throttled フラグ** / CPU 温度 / コア電圧 / サービス状態
- `fsync` で書き込みを確定し、`latest.txt` は一時ファイル + rename で
  原子的に更新するので、**書き込み中に電源が落ちても壊れない**
- **UI サービスには触れない**(journal を読むだけ)ので、試験中でも
  投入・停止できる

`throttled` を記録している理由: bit0 が立つと 5V が電圧降下したことを
意味する。**「電池が尽きた」のか「モバイルバッテリーが自動オフした」のか**を
後から区別できる(自動オフなら電圧降下なしに切れる)。

### 使い方

```bash
# 常駐させる
sudo systemctl enable --now epaper-runlog
# 電源断のあと、最後に残った値を見る
cat ~/runlog/latest.txt
tail -5 ~/runlog/epaper-run.csv
```

最悪でも**直近 1 分ぶんしか失われない**(記録間隔 = `PERIOD_S`)。

## 4. 測定方法

**変更は 1 つずつ、同条件で比較する。** まとめて適用すると効果が分からない。

1. USB 電力計を Pi の電源ラインに入れる
2. 条件を揃えて測る: ①デモ実行中(パネル更新の瞬間)②サイクル間の待機中
   ③LCD 消灯時。待機中の値が今回の主対象
3. 変更 → 再起動 → 同じ 3 条件を測る

## 5. 桁で下げたい場合(アーキテクチャの話)

「もっと下げたい」の答えは**ホストを止めること**だが、本システムでは
構造的な制約がある。

- **ESP32 に替えても解決しない**。ESP32 の deep sleep は数十 µA だが、
  それは USB ホストを維持できない状態。パネルへ指令を出し続けるなら
  起きている必要があり、結局同じ壁に当たる
- **本当の低電力化はパネルの自律再生を使うこと**。プロトコルには
  再生開始(0x16、開始スロット + 間隔秒)があり、これを使えば
  ホストの電源を切っても**パネル単体でループ再生**できる。
  ただし**書き込めるのはスロット 19 のみ**(0〜18 はメーカーデータで
  書き込み禁止)なので、**自前の絵を複数枚ループさせることは現状できない**
- 例外: **表示内容がメーカーのデモで良いなら、ホストは完全に不要**。
  電源投入時のオートプレイがそれであり、この場合の待機電力はゼロ

つまり「自前の演出を流し続けたい」という要件がある限り、
ホストは起きているしかない。→ **0.4〜0.5W が現実的な下限**。

## 6. 進め方の提案

1. ロングランテスト完了を待つ
2. **まず A-2(HDMI)・A-3(LED)・A-4(サービス)を適用**。
   我々のコードに触れずに済み、リスクが低い。ここで一度測定
3. 次に **A-1(LCD 自動消灯)を実装**。コードに触れるのはここだけ。
   消灯までの時間は設定可能にする(既定 5 分など)
4. 測定結果を見て、B-1(クロック)まで踏み込むか判断
5. Wi-Fi(C-1)は触らない

**費用対効果の確認を先に**: 常時給電の展示用途なら、0.5W の削減は
年間で数十円程度。バッテリー運用や多数台展開でなければ、
労力に見合わない可能性がある。目的(電気代 / 発熱 / バッテリー持ち)を
はっきりさせてから着手するのが良い。
