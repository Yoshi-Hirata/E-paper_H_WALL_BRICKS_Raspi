# 無停止化の設計(ファッションショー運用向け)

作成: 2026-08-06。**設計のみ。実装はロングランテスト終了後。**

## 1. 要件

ショー本番では**表示が止まらないこと**が最優先。多少の遅延や 1 サイクルの
取りこぼしは許容できるが、**「エラーで停止したまま人手を待つ」状態は許容
できない**。運転中に人が触れる可能性もあるため、誤操作でも止まらないこと。

## 2. 現状の問題

### 2.1 1 回の ACK 欠落で全体が停止する

`ui/runner.py` の `_request()` は ACK が得られないと `False` を返し、
`_run()` がそのまま `return` してワーカースレッドが終了する。
結果、**パネルはその時の絵で固まり、ボタンを押すまで復帰しない**。

### 2.2 実際に起きている

今回のロングランでも起動直後に発生していた:

```
10:56:25 start SOLID+RANDOM
10:56:27 ERROR stop @01 no ACK     ← ここでデモが停止
10:56:37 cycle 1 SOLID shown       ← 人が押し直して再開
```

原因はほぼ確実に**電源投入直後のメーカーオートプレイでパネルが
リフレッシュ中**だったこと。リフレッシュ中の基板はコマンドに応答しない
(実測 9.8 秒)。つまり**正常な一過性事象で停止している**。

### 2.3 表示コマンドだけ成功を確認していない

停止(0x17)と色保存(0x13)は ACK で確認しているが、**最も重要な
単張表示(0x1D)はブロードキャストで送りっぱなし**(仕様上 ACK なし)。
このフレームが落ちると、保存は成功しているのに絵が変わらない。

## 3. 設計: 多層リトライ

### L1. フレーム再送(既存・変更なし)

`transport.py` が 500ms タイムアウトで 3 回再送。ここは触らない。

### L2. コマンド単位のバックオフ再試行(新規)

L1 で駄目でも諦めず、**指数バックオフで再試行**する。
リフレッシュ中(9.8 秒)を待ち切れる長さにするのが肝。

| 試行 | 待ち |
|---|---|
| 1〜3 | L1 内で 0.5 秒 × 3 |
| 4 | +1 秒 |
| 5 | +2 秒 |
| 6 | +4 秒 |
| 7 | +8 秒 |
| 8 以降 | +12 秒(上限)|

- `ACK_BUSY (0x82)` は仕様どおり 1 秒待って再試行(最大 5 回)
- **色保存(0x13)だけは再試行回数を絞る**(既定 3 回)。
  毎回フラッシュ書き込みが走るため、失敗を高速に繰り返すと寿命を削る

### L3. サイクル単位の再試行(新規・最重要)

L2 を尽くしても駄目なら、**そのサイクルだけ諦めて次サイクルへ進む**。
**デモは絶対に止めない**。次サイクルは「初回扱い」に戻し、
停止 + スロット設定からやり直す(基板が再起動していても復帰できる)。

```
サイクル失敗 → ログに記録 → 次のインターバルまで待つ → 初期化からやり直す
```

パネルは前の絵を保持したままなので、**見た目は「1 回更新が飛んだ」だけ**。

### L4. バス再オープン(新規)

USB の再列挙・ケーブル抜けに対応する。以下のいずれかで発動:

- `SerialException` / `OSError` を捕捉したとき
- サイクル失敗が 3 回連続したとき

処理: バスを閉じる → 2 秒待つ → **`find_port()` からやり直す**
(デバイス名が変わる可能性があるため)→ 開き直して初期化。
ポートが見つからなければ 10 秒間隔で待ち続ける(**諦めない**)。

### L5. プロセス監視(新規)

ハング(クラッシュではなく無応答)に備え、systemd のウォッチドッグを使う。

- サービスを `Type=notify`、`WatchdogSec=120` にする
- メインループから定期的に `WATCHDOG=1` を送る
- 送られなくなれば systemd がプロセスを再起動(`Restart=always` は設定済み)

## 4. 表示コマンドの確実性(2.3 への対策)

ブロードキャスト表示は ACK が無いため、**取りこぼしても気づけない**。
対策は 2 案。**A を推奨**。

**A. ブロードキャストを複数回送る(推奨)**
同じスロットの表示指示なので冪等。1 回目でリフレッシュが始まれば
基板は 2 回目を無視する(リフレッシュ中は応答しない性質を利用)。
150ms 間隔で 3 回送れば取りこぼし確率は無視できる。
**2 枚の同時性を保てる**のが利点。

**B. 宛先指定で送って ACK を確認**
確実性は上がるが、基板ごとに順次送るため**リフレッシュ開始がずれる**。
2 枚の同時更新という演出上の要件を損なうので、**A で駄目なときの次善**。

## 5. 運用面の保護

### 5.1 ボタンロック(ショーモード)

**現状、KEY1 を押すとデモが止まる。** 本番で人や衣装が触れれば止まる。

- サービスに `--locked` を追加し、**ボタン入力を無視**する
- 解除は**長押しの組み合わせ**(例: KEY2 + KEY3 を 3 秒)に限定
- 画面には `LOCKED` を表示して状態を明示

### 5.2 本番前チェック

`python -m ui.main --check` を拡張し、**両基板が ACK を返すこと**まで
確認する(現状はポート・SPI・GPIO・LCD まで)。ショー開始前に 1 回叩く。

### 5.3 監視

`~/runlog/latest.txt` に既にサイクル数・稼働時間・エラー数が出る。
本番中は `errors` の値が増えないことを見ておけばよい。

## 6. パラメータ(実測に基づく)

| 項目 | 値 | 根拠 |
|---|---|---|
| リフレッシュ所要 | 9.8 秒 | 実測(色によらず一定) |
| L2 バックオフ上限 | 12 秒 | リフレッシュを 1 回待ち切れる長さ |
| L2 最大試行 | 8 回(約 40 秒) | 2 回ぶんのリフレッシュを跨げる |
| 色保存の再試行 | 3 回 | フラッシュ寿命とのトレードオフ |
| バス再オープン発動 | 連続 3 サイクル失敗 | 一過性と恒久故障の切り分け |
| ポート待ち | 10 秒間隔で無限 | ケーブルを挿し直せば自動復帰 |
| ウォッチドッグ | 120 秒 | 最長サイクル(60 秒)+ 余裕 |

## 7. テスト計画(ハードウェア不要)

`FakeBus` を拡張して障害を注入し、**「止まらないこと」を回帰テストで固定**する。

- `N 回失敗してから成功` → サイクルが最終的に成功し、デモが動き続ける
- `常に失敗` → デモは停止せず、サイクルを跨いで再試行し続ける
- `SerialException を投げる` → バス再オープンが走り、復帰する
- `find_port が None を返し続ける` → 例外を出さず待ち続ける
- `20% の確率でランダムに失敗` → 100 サイクル走り切る(カオステスト)
- `ACK_BUSY を返す` → 1 秒待って再試行する
- **回帰の要**: どのケースでも `runner.running` が False にならないこと

## 8. 実装順序

1. `FakeBus` に障害注入を追加し、**先に失敗するテストを書く**
2. L2(コマンド単位バックオフ)+ L3(サイクル単位再試行)
3. L4(バス再オープン)
4. 表示コマンドの複数送信(4-A)
5. `--locked`(5.1)と `--check` 拡張(5.2)
6. L5(systemd ウォッチドッグ)
7. 実機で確認: **USB ケーブルを抜き差ししても自動復帰すること**を目視

**ショー当日の推奨手順**: 事前に `--check` → 本番は `--locked` で起動 →
`latest.txt` の `errors` を時々確認 → 予備機を 1 台用意しておく。
